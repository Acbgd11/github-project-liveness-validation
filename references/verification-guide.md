# 项目存活与可用性检查指南 v1.2

## 检查深度与停止条件

| 深度 | 适用情况 | 最小覆盖 |
|---|---|---|
| 初筛 | 批量找候选 | 官方身份、用途、归档/弃用/迁移、环境硬门槛、明显目标功能故障；写明未完成标准验证 |
| 标准验证 | 正式推荐、比较或准备采用 | README/安装说明、有效提交、发布或分发渠道、目标相关问题与处理、功能证据、环境和依赖前提 |
| 深入验证 | 重要长期依赖、证据冲突、高迁移成本 | 标准验证加关键依赖链、维护者持续性、目标版本 CI/发布证据及获准的最小功能测试 |

不强制穷尽所有 Issues 或跑所有工具。若已有明确阻断且足够可信，可停止该候选的执行测试并说明依据；若关键事实已覆盖且无冲突，结束取证。访问失败可尝试一个已授权的替代渠道；继续受限则记录未知，不无限重试或绕过权限。

## 项目类型与动态时间窗口

以下范围只是开始搜索时的参考，必须结合项目自身发布节奏、用户所需版本和上游变化调整，不能单靠天数判定死亡。

| 类型 | 检索起点 | 优先验证 |
|---|---|---|
| 下载器、爬虫、逆向签名、浏览器自动化、API/模型适配 | 最近 30–90 天，并覆盖最近一次上游破坏性变化之后 | 目标站点/API/认证仍可用；成功报告和修复是否针对当前接口；关键外部服务是否仍提供 |
| 应用、SDK、框架、依赖较多的库 | 最近 90–180 天与最近几个发布周期 | 支持的运行时/平台、维护者回应、重要修复有没有进入可安装版本 |
| 稳定 CLI、纯算法、离线工具、完成的规范 | 最近 6–12 个月起，必要时回看上一稳定版 | 可复现功能、环境兼容、是否仍有未处理的关键问题；无需追求频繁提交 |
| Awesome 清单、文档、Skill、模板 | 按内容主题的变化速度选择窗口 | 条目用途与入选理由、链接实际内容、过时指令、被引用工具的状态；文档改动可构成核心维护 |
| 刚建立的新项目 | 从创建到当前的全部相关历史 | 样本不足、交付/测试质量及维护承诺；不能仅因不到某个年龄扣为“不维护” |

若 API 昨天已改变，三天前的成功示例也可能失效；若离线工具依赖和输入格式多年稳定，两年前的最后提交也不构成失败证据。不同类型不能直接比较提交频率或 Issue 数量。

## 标准检查清单

按适用性标为 `通过 / 风险 / 未知 / 不适用`，不要把“不适用”或取数失败填成 0。

- [ ] **对象和范围**：官方仓库身份、实际默认分支、目标功能/版本/安装来源；fork 与原仓库分开评估，迁移目标重新核验。
- [ ] **状态声明**：Archived、Deprecated、停止支持、迁移公告、README 警告、置顶 Issue；标明该声明覆盖的版本/功能。
- [ ] **有效维护**：提交日期及具体改动、维护者回应、问题分诊；区分代码、文档、依赖、自动生成和纯机器人活动。
- [ ] **可交付修复**：稳定版、预发布/nightly、包管理器/容器/源码分发；修复所在版本和用户安装方式匹配。没有 GitHub Release 时检查项目真实分发习惯。
- [ ] **真实反馈**：最近更新与目标相关的 open/closed 问题、评论及相关 PR；同时寻找成功和失败证据，注明抽样范围。
- [ ] **解决路径**：Issue 关闭原因、维护者说明、修复提交、合并状态、发布版本及验证反馈；不把“已计划”当“已交付”。
- [ ] **功能证据**：成功样例、目标功能测试或有环境信息的近期用户反馈；只安装/启动成功时保留核心功能未知。
- [ ] **环境适配**：OS、CPU 架构、运行时版本、CPU/GPU/内存、依赖、网络、账户/订阅/费用、必要许可证信息。
- [ ] **依赖与服务**：关键直接依赖及可能阻断的传递依赖、EOL/弃用、目标版本兼容、上游接口是否关闭；不因“有新版”自动认定旧依赖不安全或项目已死。
- [ ] **证据质量**：链接可复核、获取日期与事件日期分开、工具版本/数据快照/覆盖率清楚、关键矛盾已说明。
- [ ] **验证边界**：实际执行、未执行、因权限/成本/网络无法执行；使用真实用户数据或外部服务前确认已有授权覆盖。

## 维护与反馈的读法

先抽查默认分支最近约 3–5 个提交和约 10–20 条近期更新的 Issue/PR，并按目标功能检索。样本不够时扩大；这些数量是节省时间的起点，不是通过标准。不要以第一页结果声称检查完整历史。

- 提交标题只用于定位，要看与目标有关的实际 diff。机器人依赖更新有价值，但不证明有人复核，也不证明关键故障已修复。
- 文档、规则、数据集项目的有效内容更新可以是核心维护；对可执行工具，仅更新 README 或徽章不足以证明代码功能正常。
- 检查真人首次回应、问题到修复的时间和待处理趋势，可借鉴 CHAOSS；小样本写“抽样观察”，不伪造统计。单维护者或少量 PR 是持续性风险，不能自动判死。
- REST 的 Issues 列表可能包含 PR，应识别 `pull_request`；`open_issues_count` 也不能直接当未解决 bug 总数。
- 关闭原因包括已完成、重复、拒绝、过期、迁移。即使标为 completed，也需查修复内容；Stale Bot 关闭不是修好。
- 不启用 GitHub Issues 时，查官方支持渠道、邮件列表或其他跟踪器。无投诉不等于无故障，投诉多也可能只是用户多。
- CI 需核对 commit/ref、运行日期、平台矩阵、执行步骤和覆盖功能。徽章可能过期；lint 通过、跳过的测试或 `continue-on-error` 不等于端到端功能通过。

## 红旗及其影响

| 红旗 | 如何处理 |
|---|---|
| 作者停止支持、迁移或归档 | 新采用通常不建议；历史复现/完成规范/固定离线版本可说明例外及维护边界 |
| 当前目标功能有可复现故障、必需服务关闭，且没有适用修复 | 不建议该用途；优先查替代方案，不被 Star 或近期提交抵消 |
| 操作系统、架构、运行时、硬件或账户条件明确不满足 | 不建议当前环境；只有确认的可接受方案才能降为谨慎推荐 |
| 修复仅在未合并 PR、源码 main 或 nightly，稳定安装包尚未包含 | 不能推荐现有稳定版为已修复；说明试用条件和代价 |
| 只有机器人/徽章活动，关键故障长期无人处理 | 深挖维护证据；可证实阻断则不建议，否则降低置信度 |
| 下载/身份/许可信息冲突，或发现与采用直接相关的严重安全问题 | 暂缓采用并转交所需审查；不要把存活评估充当安全认证或法律结论 |
| API 返回错误、全零统计、数据停更、缓存陈旧、权限缺失 | 标记采集失败或未知；修复/交叉核对数据来源后再解释结果 |

## 证据、置信度与结论

不存在对所有问题通用的来源排名：作者公告最适合证明停止维护，目标版本的可复现测试最适合证明具体功能。官方文档是支持声明，不自动等于运行事实。第三方报告保留版本、环境和日期；聚合器、总分及搜索摘要只作线索。

| 置信度 | 含义 |
|---|---|
| 高 | 决定结论的事实有直接、及时且适用于目标范围的证据，关键冲突已解决；明确官方弃用声明可单独支持高置信度不建议 |
| 中 | 主要一手信息齐备，有相关功能/反馈证据，但本机复现、版本对应或部分前提尚未确认；缺口不改变已有事实 |
| 低 | 关键内容无法访问、样本陈旧、版本/环境不明或有未解释的冲突；通常应证据不足 |

置信度应按维护、功能、适配分别判断，需要单一总体置信度时由决定推荐的关键事实限制，不取三项平均。不能因为仓库身份确定，就给功能可用性高置信度。

- **推荐**：目标功能直接证据充分，环境/版本匹配且无关键阻断；外部实测可支持推荐，但必须标注自己未本机实测。
- **谨慎推荐**：用途有正向依据，存在可接受且说清的维护、兼容或验证限制；不能用于掩盖目标功能完全未知。
- **不建议**：已确认的阻断或风险超出该用途容忍度；说明能否通过不同版本/环境改变结论。
- **证据不足**：决定用途的事实仍未知或矛盾；列出最小补证动作，不硬排高低。

默认不制造 0–100 总分或精确成功概率。用户要求量化时，先定义适用于同类项目的维度/权重、数据日期、缺失项及红旗规则；缺失不记 0，关键阻断不由平均分抵消。

## 可移植的取证方式

优先已有网页/连接器；没有专用工具可使用官方 REST API。下面是相对 `https://api.github.com` 的只读路径，占位符必须先替换，分支/路径参数要正确编码；不依赖某种 shell 或 `grep` 解析 JSON。

| 目的 | API 路径/处理 |
|---|---|
| 仓库身份、归档、默认分支 | `GET /repos/{owner}/{repo}` |
| 默认分支说明 | `GET /repos/{owner}/{repo}/readme?ref={default_branch}`；按响应 encoding 解码 |
| 默认分支提交与 diff | `GET /repos/{owner}/{repo}/commits?sha={default_branch}&per_page=5`；再 `GET /repos/{owner}/{repo}/commits/{sha}` |
| 发布列表 | `GET /repos/{owner}/{repo}/releases?per_page=10`；区别 draft、prerelease、稳定版和包组件 |
| 最近更新的反馈 | `GET /repos/{owner}/{repo}/issues?state=all&sort=updated&direction=desc&per_page=20`；分离 PR，按需读取评论 |
| PR 的真实合并状态 | `GET /repos/{owner}/{repo}/pulls/{number}`；查看 `merged_at` 和 `merge_commit_sha` |
| 目标版本 CI | `GET /repos/{owner}/{repo}/actions/runs?head_sha={sha}`；必要时读 jobs/steps，缺权限记未知 |

使用结构化解析器读取完整 JSON；遵循服务实际返回的分页链接或游标，不凭第一页或假定的 last 页计算总数。403/429 需区分权限、配额和风控，404 需区分路径/迁移/私有访问权限与已删除；不能直接判死。

`updated_at` 和 `pushed_at` 均不保证默认分支核心功能仍在维护；核对提交改动、committer/author 日期与发布/反馈。不要把异常未来时间转换成正常的新鲜度。

网络受限时只用当前环境已确认可用且已授权的配置，不硬编码本机代理，不把镜像作为最终证据，也不要求用户把 Token 粘贴到聊天或输出中。
